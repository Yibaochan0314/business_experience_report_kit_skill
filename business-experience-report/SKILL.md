# 业务体验分析报告生成器

把一次「产品/业务体验」变成一份**能拿去面试或汇报的、结论有据可查的 HTML 报告**。

核心判断：报告的价值不在「我把产品点了一遍」，而在**你回答了一个具体的业务问题，并且允许证据推翻你的假设**。功能罗列是体验记录，不是分析报告。

## 何时使用

满足以下任一条即加载本 skill：

- 用户给出「某个产品/官网链接 + 想搞清楚的业务问题」，要求产出体验分析报告
- 用户给出「求职 JD + 产品体验材料」，要求产出求职作品集报告
- 用户要求诊断某产品的**试用激活率 / 付费转化率 / 留存**偏低原因
- 用户要求按 `业务背景 / 业务诊断 / 业务解决方案` 三层结构产出分析文档

不适用：纯竞品功能对比表（用竞品分析类 skill）、纯 UI 走查（用视觉评审类 skill）、无体验对象的纯方法论写作。

## 五类输入（缺哪类就走哪类降级）

| # | 输入 | 必需性 | 缺失时的降级策略 |
|---|---|---|---|
| 1 | **体检目的**：要回答的那个业务问题 | 必需 | 若用户只说「体验一下」，先反问「你最想回答哪个问题」。无目的不写报告 |
| 2 | **体验对象**：官网链接 / 产品入口 | 必需 | 无链接则要求用户给出产品名，用公开检索替代实操 |
| 3 | **JD 或能力对标基准**（求职场景） | 求职场景必需 | 无 JD 则报告不写「岗位对标附录」，改为纯业务分析 |
| 4 | **实机体验材料**：账号 / 截图 | 强烈建议 | **登录受阻时先停下来**：向用户索取其本人登录后的业务截图（见 `references/08-screenshot-request-and-review.md`），拿到后再继续。仅当用户明确回复「无法提供」时，才退回公开信息口径继续，并在摘要与附录 A 显著标注未实测范围 |
| 5 | **视觉参考图** | 可选 | 无参考图则用 `references/06-visual-system.md` 的默认 B 端蓝渐变基线 |

**先对齐再动笔**：拿到输入后，先用一张表复述理解（报告定位 / 数据口径 / 视觉基线 / 待补材料），得到用户确认后才开始检索与写作。若用户要求「先确认再执行」，任何修改都走「先说明 → 找原因 → 给方案 → 等确认」，未确认不动手。

## 工作流（9 步，按序执行）

### 第 1 步｜口径对齐
按上表复述理解并确认四件事：**报告定位**（求职作品集 / 内部汇报 / 方法论演练）、**数据口径**（实测 / 公开信息 / 推演假设）、**视觉基线**（参考图或默认）、**待补材料清单**。定位决定深度与呈现风格，定位写错等于全篇重做。

### 第 2 步｜输入采集
读 `references/01-intake-and-align.md`。逐项登记输入，把「用户提供的原始材料」与「你检索到的公开材料」分成两栏，后者必须记 URL。截图先落盘到 `shots/`，按**证据用途**命名（不是按页面顺序），例如 `w01-home-guide.jpg`、`w05-hr-subaccount.jpg`。

### 第 3 步｜取证（三条线索并行）
1. **公开信息**：抓官网首页 / 定价页 / 帮助中心原文，提取原文中文表述与数字，不要转述
2. **背景检索**：检索公司背景与营收、行业格局与渗透率、第三方评价与吐槽。真实用户的抱怨就是最好的根因线索
3. **实机体验**：加载 `agent-browser` skill，按「注册 → 登录 → 试用激活 → 核心功能 → 付费入口」走一遍，每步截图

**⛔ 闸门一：登录受阻时必须停下来**

若实机体验在登录环节被拦住（安全校验 / 账号失效 / 试用未激活 / 关键模块无权限），**不要带着「未实测」的声明直接往下写报告**。此时：

1. 如实说明卡在哪一步并截图取证（这本身就是「登录摩擦点」证据，后面写进 2.1）
2. **不绕过安全校验**，改用索取截图的方式补齐事实
3. 按 `references/08-screenshot-request-and-review.md` 输出一份**截图索取清单**：要截哪些页面、从哪进入、画面要包含什么、每张对应哪个待验证判断。按「必需 / 加分」分档，不要一次性要太多
4. **等用户回传截图后再进入第 4 步**

只有用户**明确回复无法提供**截图时，才退回公开信息口径继续；此时必须在摘要与附录 A 两处声明未实测范围，并给根因表中依据文档推测的条目加 `待实测校准` 标记。

> 为什么必须停下：一次真实返工就是先按帮助文档推测出 P0 根因、写完整份报告，后来用户补的工作台截图直接推翻了它。宁可暂停一轮，也不要白做一整轮。

### 第 4 步｜业务诊断（本报告的核心）
读 `references/03-diagnosis-playbook.md`，按四段推进：

1. **定义激活标准**——优先复用产品方已有口径（如官方「连续 N 周活跃 = 种子用户」），不另造一套语言
2. **搭漏斗定位流失**——画出「触达 → 注册 → 首次登录 → 完成建档/关键动作 → 激活」漏斗，标出**最大断崖**
3. **多维下钻**——在最大流失环节做 `行为分层 × 来源分层 × 定量 + 定性` 交叉
4. **输出根因并分级 P0/P1/P2**，结论必须能填进这个句式：**「是谁、在哪个环节、因何流失」**

每个环节同时给「亮点」与「不足」。只列问题的报告像吐槽，不像分析。

**每条根因必须标注证据类型**（`实测` / `官方文档` / `用户原声` / `推演`，见 `references/05-evidence-and-sourcing.md`）。凡标为「官方文档」而非「实测」的根因，都要带上 `待实测校准` 标记——这类条目正是闸门二核对清单的第一优先级。

### 第 5 步｜业务解决方案
读 `references/04-solution-playbook.md`：

1. **先定义问题标准**（什么状态算解决），再建可衡量指标体系（北极星 + 驱动 + 健康三层）
2. 按 **3 / 6 / 12 个月**三阶段规划，每阶段给：里程碑、达成效果预估、配合部门、资源投入
3. 每阶段显式标注方法论映射：`AARRR`（大盘增长）/ `RFM`（存量分人群）/ `CLM`（全生命周期）/ `5A`（品牌内容种草）
4. 给**验证方案有效性的方法**（A/B 或前后对比 + 样本与周期）、**指标监测体系示例图**、**落地路径与 RACI**

### 第 6 步｜JD 能力对标（求职场景必做）
把 JD 每一条职责逐条映射到报告章节，做成矩阵表并标注「已覆盖 / 缺位」。**缺位的必须补写**——那正是面试官要核对的地方。补完后在报告末尾加附录「岗位能力对标自查」，逐条列出「JD 职责 → 报告第几章答了什么 → 自评」。

宁可少一个漂亮图表，也不能有一条 JD 职责在报告里找不到落点。

### 第 7 步｜建档 HTML
1. 若用户给了视觉参考图：读 `references/06-visual-system.md`，先解析出**设计令牌**（主色渐变、圆角、字号层级、药丸标签、指标卡）并复述给用户确认
2. 复制 `assets/report-skeleton.html` 作为骨架，按 `references/02-report-outline.md` 的三章骨架填充
3. **截图按「发现的问题」分组**（用 `.evi` 证据组组件），每组含「组标题 + 截图 + 读法」，并把结论引回根因编号。不做按页面顺序的图片墙
4. 修 HTML 用补丁脚本：**先备份 `.bak`，每个替换都加 `assert s.count(old) == 1` 断言**。直接手改大文件极易产生静默错配
5. 用 `scripts/build_single_file.py` 把 `shots/*.jpg` 内联为 base64，产出单文件成品。**不要手写 base64**

### 第 8 步｜视觉评审与交付
1. 用 `scripts/audit_visual.js` 在浏览器跑自动审计：对比度（AA 4.5:1 / 大字 3:1）、横向溢出、断图数。**审计必须跳过渐变背景**，否则会把封面整片误报为不合格
2. 渲染截图目视复核关键区域（封面、图示、阶段卡），修到审计归零
3. 导出 PDF：`@page { size: A4; margin: 12mm }`，卡片类加 `break-inside: avoid`，检查无空白页
4. 用 `scripts/check_report.py` 跑交付自检
5. 交付三件：**单文件 HTML**（可分享）+ **PDF** + **`report.src.html`**（截图走相对路径，方便用户后续自己改文字）

若已安装 `report-visual-reviewer` skill，可在第 8 步调用它做对抗性视觉评审。

### 第 9 步｜交付后核对（必做，不可省略）

报告交付**不等于任务结束**。交付时必须在**对话里**附一份**核对清单**，请用户对照其本人登录后的截图逐条复核。

**硬性要求**：
- **只在对话里给**——不生成独立文件，也不写进报告附录。核对清单是过程工具，放进报告会让阅者觉得作者对自己的结论没把握
- 按「最需要核对」排序，不按章节顺序
- 每条同时给出「报告中的原话」与「需要你确认什么」，让用户能直接判定

**四类待核对内容（按优先级）**：
1. **由文档推测得出的结论**——最需要核对，因为它们是「没实测就下的判断」
2. **推演数值**（比率、金额、规模）——问用户手上有没有真实值可替换
3. **功能清单与「已落地 / 规划中」的判定**
4. **角色与业务归属**（某能力面向谁、实际谁在用）

**收到反馈后**：
1. 逐条记录，区分「改结论 / 改措辞 / 补证据」
2. 用补丁脚本改 HTML：先备份 `.bak`，每个替换加 `assert s.count(old) == 1`
3. 若反馈推翻原结论，**不要静默改掉**——按 `05-evidence-and-sourcing.md` 的「被推翻的假设」模板保留推敲过程（这是报告最有说服力的部分）
4. 重跑第 8 步的 `audit_visual.js` + `check_report.py`，重新导出 PDF

模板与两道闸门的完整说明见 `references/08-screenshot-request-and-review.md`。

## 交付契约

| 交付物 | 要求 |
|---|---|
| `<产品名>-业务体验分析报告.html` | 单文件，图片全内联，双击即可打开与分享 |
| `<产品名>-业务体验分析报告.pdf` | A4，无空白页，打印分布合理 |
| `report.src.html` | 可编辑源文件，截图走相对路径 |
| `shots/` | 原始与压缩截图，命名体现证据用途 |
| **核对清单**（对话内，不落文件） | 交付时同步给出，四类待核对内容按优先级排列，等用户复核 |

报告必须能独立回答：**报告定位是什么、数据口径是什么、结论建立在什么证据上、哪些是推演、哪些还没实测**。

## 质量红线（违反即不合格）

- **不编造数据**。所有数字标注来源；推演值必须显式写「基于公开信息的推演值（非官方数据）」
- **不绕过安全校验**。验证码、风控一律不绕，如实记录为体验摩擦点
- **登录受阻不擅自降级产出**。必须停下来向用户索取实测截图；未索取、也未取得用户「无法提供」的明确答复，就带着「未实测」写完整报告，算不合格
- **不用文档推测冒充实测结论**。判断来自帮助文档而非实操时，写明「依据帮助中心文档，待实测校准」，并在根因表中打标记
- **交付必须附核对清单**。报告不是发出去就结束——要把「哪些结论还没被账号持有人确认过」显式交还给用户核对
- **证据推翻假设时，改写结论并保留推敲过程**。这一条本身是报告最有说服力的部分——它证明你在做分析，不是在填表
- **不裸奔结论**。每条根因都要能定位到「谁 / 哪个环节 / 因什么」
- **不省略 Non-goals**。给方案时明确写「本阶段不做什么」，防止范围蔓延
- **不写空话亮点**。亮点要能指出「哪个能力已经落地」，未上线的功能标为「愿景 / 规划中」

### 接收方安装检查清单（防止装成旧版）

本 skill **不会自动更新**。若对方原本已装过旧版，或解压时不注意，就会继续按旧规则产出报告——最典型的后果是**跳过闸门一**，回到「登录受阻也照常出报告」的老路。

| # | 检查项 | 怎么看 |
|---|---|---|
| 1 | **版本号对不对** | 打开 `<skill>/SKILL.md`，看 frontmatter 的 `version`。与你告知的版本号不一致即为旧版 |
| 2 | **装之前旧目录删了吗** | 必须**先删掉旧目录**再放新目录。两份目录名不同（如 `business-experience-report` 与 `business-experience-report (1)`）会让**新旧两个技能并存**，触发时可能命中旧版 |
| 3 | **目录名有没有被改名** | 必须仍是 `business-experience-report/`。加分后缀、加日期后缀都可能造成并存 |
| 4 | **快照有没有误放进 `skills/`** | 快照目录（`skill-snapshots/`）内是**完整含 `SKILL.md` 的一份副本**。若被放进 `skills/`，会被扫描器当成独立的技能包加载，等于同一技能出现两个版本 |

**一条问句就能验证装的是哪版**：装完后直接问 AI——

> 「这个 skill 的工作流是几步？登录受阻时该怎么做？」

- 回答「**9 步** + 登录受阻**先停下索取截图**」→ 新版（≥1.1.0）
- 回答「**8 步**」或「声明未实测后继续」→ **旧版，需要覆盖安装**

## 维护与版本管理

本 skill 用「`version` 字段 + `CHANGELOG.md` + 快照目录」三件套做版本管理。

**改动 skill 后按序做三步**：

1. **升版本号**——改 `SKILL.md` frontmatter 的 `version`（新增能力升 minor、修正错误升 patch）
2. **写变更记录**——在 `CHANGELOG.md` 顶部追加一条，写清「改了什么 / 为什么改 / 怎么验证的」，**不修改历史条目**
3. **留快照并重打包**——跑 `bash scripts/snapshot.sh`，然后重新打包 zip

**为什么必须留快照**：快照是「可回滚 + 可 diff」的基线。没有它，日后想知道「新版是否包含旧版的全部内容」只能靠回溯对话记录（间接证据，且记录可能已被清理）；改坏了也没有退路。**版本号解决「可验证」，快照解决「可回滚」。**

**三点约定**：
- 快照默认输出到 `<skill 的上两级>/skill-snapshots/`（用户级 skill 即 `~/.workbuddy/skill-snapshots/`），**刻意放在 `skills/` 之外**，避免被 skill 扫描器误识别成一个技能包；要改位置就传参数
- 脚本同日同版**幂等**：重复执行只提示「已存在」，不会重复留档。修正后想再留快照，先升 version
- 快照脚本自身也会被复制进快照，所以快照是「含当时机制的完整态」
- **不要把快照目录挪进 `skills/`**：快照内含完整 `SKILL.md`，放进去会被扫描器识别成一个独立技能，导致同一 skill 出现两个版本、路由到旧版。要换位置用参数指定到 `skills/` 之外

**分发给他人时**：告知对方版本号（对方看 `SKILL.md` 的 `version` 即可确认自己装的是哪版）。**已装旧版的需要覆盖安装**——删掉旧目录再放新目录，本 skill 不会自动更新。

## 快速验收自检

生成完成后按顺序执行：

```bash
python scripts/build_single_file.py --src report.src.html --dry-run   # 预演内联体积
python scripts/build_single_file.py --src report.src.html             # 生成单文件
agent-browser open "file:///绝对路径/报告.html"                        # 渲染
agent-browser eval --stdin < scripts/audit_visual.js                  # 视觉审计
python scripts/check_report.py --src report.src.html --pdf 报告.pdf    # 交付自检
```

审计要求：`contrast.fails = 0`、`overflowX = false`、`images.broken = 0`、`svgTextOutOfViewBox = []`；自检要求无 `FAIL`。

特别地：若正文出现「未实测」字样，自检会强制要求「摘要 + 附录 A 双处声明」与「根因表 `待实测校准` 标记」同时成立，否则判 `FAIL`——这是闸门一的自动化兜底。
