# 业务体验分析报告生成器

> 把一次「产品/业务体验」变成一份结论有据可查、可分享、可后续手动编辑的 HTML 分析报告（另出 A4 PDF）。

**核心判断**：报告的价值不在「我把产品点了一遍」，而在**你回答了一个具体的业务问题，并且允许证据推翻你的假设**。功能罗列是体验记录，不是分析报告。

它不是让 AI 帮你写一篇产品介绍，而是让 AI 按一套固定的分析规范，把体验过程变成有证据、有结论、有优先级的诊断报告。

---

## 它解决什么问题

| 场景 | 你要回答的问题 |
|---|---|
| **求职作品集** | 这个岗位要什么能力？用这份报告证明我具备 |
| **产品试用诊断** | 为什么用户注册后没被激活？卡在哪个环节？ |
| **内部汇报 / 方法论演练** | 这套方案的问题出在哪，下一步该怎么改 |

## 什么时候用它 / 什么时候别用

**用它**（满足任一即可）：

- 给出「产品链接 + 想搞清楚的业务问题」，要求产出体验分析报告
- 给出「求职 JD + 产品体验材料」，要求产出作品集报告
- 要求诊断某产品的**试用激活率 / 付费转化率 / 留存**偏低原因
- 要求按「业务背景 / 业务诊断 / 业务解决方案」三层结构产出分析文档

**别用它**：

- 纯竞品功能对比表 → 用竞品分析类技能
- 纯 UI 走查 → 用视觉评审类技能（可搭配本仓库的 `report-visual-reviewer`）
- 没有体验对象的纯方法论写作

## 你需要提供什么（五类输入）

| # | 输入 | 必需性 | 缺了会怎样 |
|---|---|---|---|
| 1 | **体检目的**——要回答的那个业务问题 | 必需 | 它不会硬写，先反问你「你最想回答哪个问题」 |
| 2 | **体验对象**——官网链接 / 产品入口 | 必需 | 无链接则要产品名，改用公开检索替代实操 |
| 3 | **JD 或能力对标基准** | 求职场景必需 | 无 JD 则不写「岗位对标附录」，改为纯业务分析 |
| 4 | **实机体验材料**——账号 / 截图 | 强烈建议 | **登录受阻时会先停下来**，给你一份截图索取清单（见「两道强制闸门」） |
| 5 | **视觉参考图** | 可选 | 无参考图则用内置的 B 端蓝渐变基线 |

它拿到输入后**先对齐再动笔**：用一张表复述理解（报告定位 / 数据口径 / 视觉基线 / 待补材料），你确认后才开始检索与写作。

## 你会拿到什么（交付契约）

| 交付物 | 说明 |
|---|---|
| `<产品名>-业务体验分析报告.html` | **单文件**，图片全内联，双击就能打开、能直接发给别人 |
| `<产品名>-业务体验分析报告.pdf` | A4，无空白页，打印分布合理 |
| `report.src.html` | 可编辑源文件，截图走相对路径——**方便你后续自己改文字** |
| `shots/` | 原始与压缩截图，命名体现证据用途 |
| **核对清单** | 交付时在对话里同步给出（不落文件），按「最需要核对」排序 |

## 报告长什么样

固定三章，每章有必填项：

| 章节 | 内容 |
|---|---|
| **一、业务背景** | 公司背景与产品定位；行业背景与目标用户画像 |
| **二、业务诊断** | 业务流程与核心路径体验（核心功能 + 业务转化流转图 + 运营手段 + 获客渠道 + 定价策略 + 亮点/不足）；激活率低的根因分析（定义激活标准 → 搭漏斗定位流失环节 → 多维度下钻 → 根因与优先级） |
| **三、业务解决方案** | 问题定义标准与可衡量指标；3 / 6 / 12 月三阶段方案（里程碑 + 效果预估 + 配合部门 + 资源投入）；方法论映射 + 验证方法 + 指标监测体系 |
| **附录 A** | 信息来源与数据口径声明（公开信息 / 用户原声 / 行业报告 / 实测四类，逐条带 URL） |
| **附录 B** | 岗位能力对标自查（求职场景；JD 每条职责 → 报告第几章答了什么） |

诊断结论必须能填进这个句式：**「是谁、在哪个环节、因何流失」**。只列问题的报告像吐槽，不像分析。

## 怎么用

不用敲命令，用自然语言触发即可：

```
帮我做一份业务体验分析报告。
JD：（粘贴岗位职责）
体验对象：https://...
体验目的：诊断该产品试用激活率偏低的原因
报告定位：求职作品集
```

求职场景会给每条 JD 职责标注「已覆盖 / 缺位」，**缺位的必须补写**——那正是面试官会核对的地方。

## 两道强制闸门

这是本技能与「让 AI 随手写一份分析」最实质的区别。

### 闸门一：登录受阻时停下来

如果实机体验在登录环节被拦住（安全校验 / 账号失效 / 试用未激活 / 关键模块无权限），**它不会带着「未实测」的声明硬写报告**，而是：

1. 如实说明卡在哪一步并截图取证（这本身就是「登录摩擦点」证据，会写进报告）
2. **不绕过验证码 / 风控**——守合规底线，也恰好是最硬的一段证据
3. 给你一份**截图索取清单**：要截哪些页、从哪进入、画面要包含什么、每张对应哪个待验证判断，按「必需 / 加分」分档
4. **等你回传截图后再继续**

只有你明确回复「无法提供」时，它才退回公开信息口径继续，并在**摘要与附录 A 两处**声明未实测范围，给推演条目打 `待实测校准` 标记。

> 为什么必须停下：一次真实返工就是先按帮助文档推测出 P0 根因、写完整份报告，后来用户补的一张工作台截图直接推翻了它。宁可暂停一轮，也不要白做一整轮。

### 闸门二：交付后附核对清单

报告交付**不等于任务结束**。交付时它会在对话里附一份核对清单，请你对照本人登录后的截图逐条复核，按优先级排：

1. **由文档推测得出的结论**（最需要核对）
2. **推演数值**（比率、金额、规模）——问你有没有真实值可替换
3. **功能清单与「已落地 / 规划中」的判定**
4. **角色与业务归属**

若你的反馈推翻了原结论，它**不会静默改掉**，而是保留推敲过程——那恰恰是报告最有说服力的部分：它证明你在做分析，不是在填表。

## 运行依赖

生成报告本身不需要你装东西；只有跑**自动审计脚本**时需要：

| 依赖 | 用途 |
|---|---|
| Python 3 | `build_single_file.py`、`check_report.py` |
| Node.js | 运行浏览器审计脚本 |
| 本机 Chrome | 渲染与截图 |
| Pillow | 截图压缩（可选） |

审计与自检命令（注意是 `--stdin`，**agent-browser 没有 `--file` 选项**）：

```bash
python scripts/build_single_file.py --src report.src.html --dry-run   # 预演内联体积
python scripts/build_single_file.py --src report.src.html             # 生成单文件
agent-browser open "file:///绝对路径/报告.html"                        # 渲染
agent-browser eval --stdin < scripts/audit_visual.js                  # 视觉审计
python scripts/check_report.py --src report.src.html --pdf 报告.pdf    # 交付自检
```

审计要求：`contrast.fails = 0`、`overflowX = false`、`images.broken = 0`、`svgTextOutOfViewBox = []`；自检要求无 `FAIL`。

## 安装与更新

技能目录名**必须**与 `SKILL.md` 里的 `name` 字段一致（`business-experience-report`），否则可能加载失败。

```bash
cp -R business-experience-report ~/.workbuddy/skills/          # 用户级：跨项目可用
cp -R business-experience-report <项目>/.workbuddy/skills/      # 项目级：团队共享
```

**本技能不会自动更新**。已装旧版的请**先删除旧目录再放入新目录**——否则新旧两个技能并存，触发时可能命中旧版。

装完后一条问句就能验证版本：

> 「这个 skill 的工作流是几步？登录受阻时该怎么做？」

- 回答「**9 步** + 登录受阻**先停下索取截图**」→ 新版（≥ 1.1.0）
- 回答「**8 步**」或「声明未实测后继续」→ **旧版，需覆盖安装**

当前版本见 `SKILL.md` frontmatter 的 `version` 字段。

## 常见问题

**Q：我没有账号、登录不进去，能出报告吗？**
能，但它会先按闸门一请你提供本人截图。你明确表示无法提供时才会降级继续，并在摘要与附录 A 两处声明未实测范围，对文档推测的条目打「待实测校准」标记。

**Q：数据是编的吗？**
不是。所有非实测数值都标注为「推演值」并说明依据，附录 A 逐条列来源与 URL。技能里明确禁止「用文档表述改写成像是实测得到的结论」。

**Q：一定要有 JD 吗？**
求职场景必需（否则附录 B 无从对标）。纯内部汇报或方法论演练可省，报告会自动去掉岗位对标部分。

**Q：能换掉默认的蓝色渐变视觉吗？**
可以。见 `references/06-visual-system.md` 的参考图解析法，把你的参考图解析成设计令牌替换即可，其余骨架不用动。

**Q：能只用这一个技能吗？**
能，全流程可独立完成。搭配 [`report-visual-reviewer`](../report-visual-reviewer/) 效果更好——第 8 步可调用它做对抗性视觉评审，输出 P0/P1/P2 分级、定位到具体元素的修改项。

## 版本与更新

本技能用「`version` 字段 + `CHANGELOG.md` + 快照目录」三件套做版本管理：

1. 改 `SKILL.md` 的 `version`（新增能力升 minor、修正错误升 patch）
2. 在 `CHANGELOG.md` **顶部**追加变更（只增不改）
3. 跑 `bash scripts/snapshot.sh` 留快照

快照是「可回滚 + 可 diff」的基线：没有它，日后想知道「新版是否包含旧版的全部内容」只能靠回溯，改坏了也没有退路。**版本号解决「可验证」，快照解决「可回滚」。**
