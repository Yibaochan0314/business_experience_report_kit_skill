# 08 · 登录受阻闸门与交付后核对

本文件定义两道**强制关卡**。它们的作用是把「准确性」的举证责任，从你的推断交还给**有账号的一方**。

> 反面教训（真实发生）：先按帮助中心文档推测出 P0 根因「协作能力被付费墙锁死」，写出完整报告；后来用户补交工作台截图，直接证明该判断不成立（子账号能力完全开放）。**等于整轮白做。** 两道闸门就是为了避免这种返工。

---

## 闸门一：登录受阻时，停止产出报告

### 触发条件（满足任一即触发）

- 登录被安全校验拦住（滑块、图形验证码、行为验证、短信验证）
- 账号无效 / 密码错误 / 账号被锁
- 登录成功但试用未激活，核心功能区不可进入
- 关键模块提示「无权限」「请联系管理员」

### 禁止动作

- ❌ 绕过或尝试绕过安全校验
- ❌ 带着「登录后未实测」的声明**直接往下写完整报告**
- ❌ 用帮助中心文档的表述，改写成像是实测得到的结论

### 必须动作（按序）

1. **如实说明卡在哪一步**，附上该环节截图（这本身是「登录摩擦点」证据，后面会写进报告 2.1）
2. **输出截图索取清单**（模板见下），一次性把需求讲清楚
3. **停下来等回传**，不要自行降级继续
4. 拿到截图后：按 `03-diagnosis-playbook.md` 重跑诊断，进入第 4 步

### 退出条件（只有这一条能解除闸门）

用户**明确回复无法提供**截图（例如：不方便登录 / 没有账号 / 公司政策不允许）。此时才退回公开信息口径继续，并且必须：

- 在**摘要**与**附录 A** 两处都显式声明未实测范围
- 根因表中凡依据文档推测的条目，加 `待实测校准` 标记
- `check_report.py` 会强制校验这三项，缺一项判 FAIL

## 截图索取清单模板

在对话里以表格输出。**按优先级分「必需 / 加分」两档，一次别要太多**——要得越多，用户越可能一张都不给。

```
为了把诊断做实，需要你在自己浏览器登录后补几张截图。
我会把每张图对应到具体要验证的判断上，你可以按重要程度选择性提供。

【必需】这 4 张决定根因能不能定下来
| # | 截哪个页面 | 从哪进入 | 画面要包含 | 用于验证 |
|---|-----------|---------|-----------|---------|
| 1 | 工作台首页 | 登录后默认页 | 整页，含左侧菜单全展开 | 引导体系密度、首屏给用户什么 |
| 2 | <空状态页> | <路径> | 顶部提示条 + 主区域 | 冷启动门槛：有没有降门槛抓手、放在哪个入口 |
| 3 | <权限/成员页> | <路径> | 列表与操作按钮 | 协作能力是否受版本限制（关键：这决定 P0 根因） |
| 4 | 顶部账户区 | 任意页右上角 | 有效期 / 版本标识 | 试用到期后的行为与付费紧迫感 |

【加分】有则更好
| 5 | <核心业务页> | <路径> | <元素> | 核心流程的真实可用性 |
| 6 | <移动端/小程序> | <路径> | <元素> | 角色覆盖广度 |

说明三点：
- 请用原图（不要经微信压缩），直接拖进对话即可
- 若画面含真实客户姓名 / 手机号，请先打码
- 如果哪张不方便截，直接说，我会把它对应的判断降级为「待实测校准」
```

### 通用「待验证判断」清单

不确定该要哪几张图时，从这张表反查——**每一项都是只有登录后才能确认、且会直接改变结论的判断**：

| 待验证判断 | 需截的页面 | 为什么关键 |
|---|---|---|
| 协作 / 多角色能力是否被版本限制 | 成员管理、权限设置 | 直接决定「协作价值是否被锁在付费墙后」这类 P0 根因真假 |
| 冷启动门槛有多高、有没有降门槛抓手 | 数据初始化 / 导入页 | 区分「产品缺失」与「运营触达没做到位」——两者解法完全不同 |
| 引导体系密度与内容 | 各模块首屏、新手引导弹窗 | 区分「没有引导」与「引导讲功能不讲任务闭环」 |
| 哪些功能已落地、哪些是规划中 | 相关功能页 | 防止把「未来规划」当亮点写 |
| 组织架构初始状态 | 部门 / 岗位 / 员工列表 | 判断用户注册后面对的是「可用系统」还是「空白系统」 |
| 试用到期后的行为 | 顶部有效期、到期提示 | 判断付费转化缺口的真实来源 |
| 运营活动是否仍在有效期 | 活动页 / 弹窗 | 识别运营断档 |
| 权限与可见范围 | 角色设置 | 判断不同画像用户实际能看到什么 |

## 闸门二：交付后核对（不可省略）

报告交付**不等于任务结束**。交付时必须在对话里附一份**核对清单**，请用户对照自己登录后的截图逐条复核。

### 硬性要求

- **只在对话里给**——不生成独立文件，不写进报告附录
  （核对清单是过程工具，放进报告会给阅者「作者对自己的结论没把握」的印象）
- 按「最需要核对」排序，不是按章节顺序
- 每条都要给出「报告里的原话」与「需要你确认什么」，让用户能直接判定

### 核对清单模板

```
报告已产出。以下 4 类内容最需要你对照截图确认，
请按「属实 / 需修正为…」回复，我据此修订并重跑审计。

【第一类·最需要核对】由文档推测得出的结论
| # | 报告中写的 | 依据 | 请确认 |
|---|-----------|------|-------|
| 1 | <结论原话> | 帮助中心文档 | 是否与实际一致？ |

【第二类】推演数值
| 2 | <比率/金额> | 公开信息推演 | 你手上有没有真实值可以替换？ |

【第三类】功能清单与「已落地 / 规划中」判定
| 3 | <功能名> 标注为「规划中」 | 页面提示 | 判定是否准确？有没有已上线的？ |

【第四类】角色与业务归属
| 4 | <某能力> 面向 <某角色> | 官网表述 | 实际谁能用？谁在用？ |
```

### 收到反馈后的修订流程

1. 逐条记录反馈，区分「改结论」「改措辞」「补证据」
2. 用补丁脚本改 HTML：**先备份 `.bak`，每个替换加 `assert s.count(old) == 1` 断言**
3. 若某条反馈推翻原结论，**不要静默改掉**——按 `05-evidence-and-sourcing.md` 的「被推翻的假设」模板保留推敲过程
4. 重跑第 8 步：`audit_visual.js` + `check_report.py`
5. 重新导出 PDF，并把新截图内联（`build_single_file.py`）

## 两道闸门的位置关系

```
第 3 步 取证
   └─ 登录受阻？ ── 是 ──▶ ⛔ 闸门一：停止 → 索取截图 → 等回传
                                                        │
                                              用户说无法提供 ──▶ 降级继续（显著标注）
                                                        │
   ┌────────────────────────────────────────────────────┘
   ▼
第 4~8 步 诊断 → 解法 → JD 对标 → 建档 → 评审 → 交付
   │
   └─▶ ⛔ 闸门二：附核对清单 → 等用户复核 → 按反馈修订 → 重跑审计
```
