# 05 · 证据与溯源协议

报告的可信度 = 每句话都能追溯到证据。这一层做不实，报告再漂亮也没人信。

## 一、证据分级

| 级别 | 类型 | 表述要求 |
|---|---|---|
| **A · 实测** | 自己实机操作得到的结果与截图 | 直接陈述，「实机验证：…」，配截图 |
| **B · 官方公开** | 官网、帮助中心、定价页、财报、公告 | 必须标来源 URL；原文表述优先于你的转述 |
| **C · 第三方** | 用户社区原声、行业报告、媒体报道 | 标出处 + 时间；区分「用户个体主张」与「统计结论」 |
| **D · 推演** | 你的假设、类比、估算 | **必须显式标注为推演值**，并说明推演依据 |

一条结论可以由多级证据支撑，但要写清哪部分实测、哪部分推演。**禁止把 D 写成 A。**

## 二、来源标注规范

正文里出现的每个数字，背后都要有落点：

- 关键数字卡 → 卡内直接写「来源：官网定价页」
- 表格中的比率 → 表下写「数据口径：…」
- 图表 → 图注写明数据来源与口径
- 附录 A 统一列全部来源，按四类分组并带 URL

附录 A 格式：

```
## 公开信息
1. 产品官网首页 —— <URL>（访问日期）
2. 定价页 —— <URL>
## 用户社区原声
1. <帖子标题> —— <平台> <URL>
## 行业公开报告
1. <报告名> —— <机构> <年份>
## 实测
- 体验账号：测试账号 1 个（凭据不记录）；体验时间：YYYY-MM-DD
```

## 三、推演 vs 实测的表述模板

**推演值**：
> 注：各环节比率为基于公开信息的推演值（非官方数据），用于确定优化优先级，需接入真实埋点后校准。

**实测值**：
> 实测：2026-10-15 使用测试账号登录，顶栏显示「有效期至 2026-09-24」。

**文档依据但未实测**：
> 依据帮助中心文档（<URL>），免费版为 1 账号；需实机校准。

**被推翻的假设**：
> 初版判断为「协作能力被付费墙锁死」（依据：帮助中心文档）。实机验证后发现不成立——人事管理模块具备「一键同步子账号 / 设置权限 / IP 白名单」（见证据 05）。结论修正为「协作能力开放，但缺少主动邀请同事的推力」。此修正过程保留，用以说明结论以实测校准。

## 四、安全与隐私红线

**不绕过安全校验。** 遇到滑块、图形验证码、行为验证等风控机制：
1. 停止操作，截图取证
2. 把该机制本身写成「登录环节摩擦点」证据
3. **不要就此降级写报告**——按 `08-screenshot-request-and-review.md` 的闸门一，向用户索取其本人登录后的业务截图，等回传后再进入诊断
4. 仅在用户明确表示无法提供时，才在**摘要**与**附录 A** 两处声明未实测范围，并给根因表中的文档推测条目加 `待实测校准`

**「待实测校准」标记规范。** 凡结论的证据类型不是「实测」而是「官方文档/帮助中心」，一律在根因表与相关结论后加此标记，建议用 `.tag t-warn` 呈现。它有两个作用：对外诚实（阅者知道哪些是推断），对内可追踪（用户补图后能精确知道该校准哪几条）。

**凭据只用于本次体验。** 用户提供的账号密码：
- 不写入记忆文件（memory）
- 不写入报告正文或附录
- 不写入日志
- 报告中只写「测试账号 1 个（凭据不记录）」

**不采集个人数据。** 截图前检查画面中是否含真实客户姓名、手机号、身份信息；有则打码或换用示例数据。

## 五、措辞规范

| 避免 | 改为 |
|---|---|
| 「功能很烂」 | 「该功能在 X 场景下无法完成 Y，导致用户必须绕行」 |
| 「用户觉得难用」（无出处） | 「社区有用户反馈『…』（出处：…）」 |
| 「应该加个引导」 | 「在该环节前置引导，预计可降低 X 环节流失，验证方式：…」 |
| 「业界第一」 | 「据 <来源>，该指标为 X」 |
| 「生态完善」 | 「已落地：A / B；规划中：C、D（页面标注为未来规划）」 |

最后一条尤其重要：**已落地能力与规划中能力必须分开写。** 把「未来规划」当亮点写，一旦被追问就是硬伤。
