## 二、逐节必填项

### 封面
- [ ] 产品名 + 视角标签（如「产品运营视角」）
- [ ] 英文 eyebrow 一行
- [ ] H1 主标题
- [ ] 副标题：**必须包含那个被回答的业务问题**，不只写「体验报告」
- [ ] 关键标签 chips（覆盖的三章 + 用到的方法论）
- [ ] meta 行三项：体验时间 / 体验对象 / 数据口径

### 关键数字卡（4 张）
选数字的标准：**每张卡都要能在正文被引用**。优先选「产品规模 / 价格 / 关键限制 / 行业背景」四类。每张卡必须写来源。

### 摘要
- [ ] 一句话结论（加粗核心矛盾）
- [ ] 双栏：左「核心矛盾（诊断结论）」右「解决主线（方案结论）」

### 1.1 公司背景与产品定位
- [ ] 公司主体、上市情况、营收与增速（带年份）
- [ ] 集团业务版图与本品的位置
- [ ] 产品一句话定位
- [ ] **护城河判断**：不是功能多，而是它占据了什么别人替代不了的位置

### 1.2 行业背景与目标用户画像
- [ ] 行业规模 / 渗透率 / 增速（有数就上数，没数写明缺失）
- [ ] 2–4 类用户画像卡：角色 + 规模特征 + 核心诉求 + 最可能卡在哪

### 2.1 业务流程与核心路径体验
- [ ] 核心板块与功能清单（尽量穷尽，来自官网 + 帮助中心）
- [ ] **业务转化流转图**（从触达到付费的全链路一图）
- [ ] 现有运营手段（含活动、激励、裂变机制，注意标注**活动是否已到期**）
- [ ] 获客渠道与来源结构
- [ ] 定价情况与策略（含免费/付费差异、抵扣规则）
- [ ] 论点—证据图分组（见下）
- [ ] 亮点 / 不足双栏（每栏 ≥4 条，都要具体到「哪个功能」）

### 2.2 根因分析
- [ ] 激活标准定义（优先复用产品方口径）
- [ ] 激活漏斗图 + 每环节比率 + **最大断崖标注**
- [ ] 多维下钻：行为分层 × 来源分层 × 定量定性
- [ ] 根因表：编号 / 根因 / 影响 / 证据 / 级别（P0-P2）
- [ ] 结论句：**「是谁，在哪个环节，因何流失」**
- [ ] 数据口径声明（推演值必须标注）

### 3.1 问题定义标准与指标体系
- [ ] 问题定义：什么状态算「已解决」，可验收
- [ ] 北极星指标（+ 为什么选它）
- [ ] 驱动指标 / 健康指标两层
- [ ] 指标树图

### 3.2 三阶段方案
每阶段必须齐 6 项：**阶段目标 / 关键动作 / 里程碑 / 达成效果预估 / 配合部门 / 资源投入**，并标注方法论映射。

### 3.3 验证方法与落地路径
- [ ] 验证方法（A/B 或前后对比，含样本量与周期）
- [ ] 指标监测体系示例图（分层，如采集层→加工层→看板层→决策层）
- [ ] 落地路径 + RACI

### 3.4 运营体系配套
四张表：试用分层 × 运营策略矩阵 / 渠道追踪与 ROI / 全流程策略查表 + 线索评分 / 内容资产清单。详见 `04-solution-playbook.md`。

### 附录 A
- [ ] 分「公开信息 / 用户社区原声 / 行业报告 / 实测」四类列来源，每条带 URL
- [ ] 数据口径与局限声明
- [ ] **若存在未实测范围，必须按下面「未实测声明规范」写**

#### 未实测声明规范（登录受阻且用户无法提供截图时）

只有在用户**明确表示无法提供**截图的情况下才会用到这一节。三处声明缺一不可，`check_report.py` 会强制校验：

1. **摘要卡**内加一条显式说明，不能只在附录里提——阅者只看摘要时就该知道哪些没实测
2. **附录 A** 的「数据口径与局限声明」写清具体范围：哪些模块、哪些结论未实测、依据什么替代
3. **根因表**中凡依据文档推测的条目，标 `待实测校准`（建议用 `.tag t-warn` 呈现）

写法示例：

> 说明：本次体验受登录环节安全校验限制，**XX 模块内部区域未实测**。相关判断依据帮助中心公开文档（<URL>）与用户社区原声，已在根因表中标注 `待实测校准`。建议由具备账号的同事完成一次实测后校准。

### 附录 B（求职场景）
- [ ] JD 每条职责 → 报告章节落点 → 自评
- [ ] 任职要求逐条对标
- [ ] 一段「本报告坚持的三件事」（用于差异化）

## 三、论点—证据图分组规范（`.evi` 组件）

**禁止**按页面顺序堆图。按「你发现的问题」分组，每组结构：

```
证据 NN ｜ <这一组要证明的一句话>
  ├─ 截图 1（+. 读法）
  ├─ 截图 2（+. 读法）
  └─ 读法框：这组图证明了什么 → 引回根因编号
```

组的划分建议 4–6 组，覆盖：引导体系 / 空状态与冷启动 / 降门槛抓手位置 / 已落地能力 vs 规划中 / 协作与激励机制。

## 四、交付自检清单

- [ ] 封面副标题包含被回答的业务问题
- [ ] 三章齐全，每章有独立结论
- [ ] 2.2 结论能填进「谁 · 哪个环节 · 因什么」
- [ ] 所有数字有来源；推演值已标注
- [ ] 根因条目均有证据支撑（实测或文档，且标明哪种）
- [ ] 亮点区分「已落地」与「规划中」
- [ ] 方案每阶段 6 项齐全 + 方法论映射
- [ ] 有 Non-goals
- [ ] 附录 A 来源齐全带 URL
- [ ] 若存在未实测：摘要 + 附录 A 均声明，根因表中对应条目带 `待实测校准`
- [ ] （求职）附录 B 覆盖 JD 全部职责
- [ ] 对比度审计归零、无横向溢出、无断图
- [ ] PDF 无空白页
- [ ] **交付时已在对话里附上核对清单**（四类待核对内容按优先级排列，未落文件、未进报告）
