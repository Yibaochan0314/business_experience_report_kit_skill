# 变更记录

记录本 skill 的版本变更，**只增不改**：新版本追加在最上方，不修改历史条目。

当前版本以 `SKILL.md` frontmatter 的 `version` 字段为准。本文件随 skill 一起分发，接收方可据此判断自己装的是哪一版、要不要更新。

> ⚠️ **本文件是历史记录，不是行为规则。** 下方旧版本条目里描述的评审做法若与现状冲突，**一律以 `SKILL.md` 为准**，本文件仅用于追溯改了什么。

## 1.1.1 — 2026-10-16

### 修复

- **`name` 字段由中文改为 hyphen-case 英文**：`报告视觉评审官` → `report-visual-reviewer`。
  - 原因：`package_skill.py` 校验要求 `name` 为 hyphen-case，中文名会导致**打包失败**（`❌ Name '报告视觉评审官' should be hyphen-case`），skill 无法对外分发。1.1.0 因此从未成功打包过。
  - 中文名「报告视觉评审官」前移至 `description` 开头，并在触发词里补入「报告视觉评审官」，**可发现性不变**——用中文名或英文标识都能路由到本 skill。
  - 已确认无连带影响：`business-experience-report` 第 8 步调用本 skill 时用的是英文目录名，未引用中文标识。

### 新增

- `SKILL.md`「维护与版本管理」新增**命名约定**一条：`name` 必须 hyphen-case 英文，中文名只放 `description`；并强调改动 `name` 后必须**重跑打包**验证，不能只看校验脚本通过（本次教训：`quick_validate.py` 与 `verify-skill.py` 对中文 `name` 均判通过，只有打包器会拦）。

### 验证

- `package_skill.py` 打包成功（1.1.0 此步失败，本版通过）
- `tiangong-skill` 的 `verify-skill.py` 结构化校验仍 PASS（`frontmatter` 字段完整、岗位型技能必需结构未被破坏）
- `quick_validate.py`：Skill is valid!
- 快照与 skill 目录逐文件 MD5 一致；目录 / 快照 / zip 三方一致

### 说明

`1.1.0` 的快照已保留（未覆盖），可据此看到「加版本机制、但 `name` 仍是中文」的中间态。本版（`1.1.1`）是**首个可成功打包分发**的版本。

## 1.1.0 — 2026-10-16

### 新增

- **版本管理机制（三件套）**
  - `SKILL.md` frontmatter 的 `version` 字段升为 `1.1.0`，当前版本以此为准
  - `CHANGELOG.md`（本文件）：记录每次变更的「改了什么 / 为什么改 / 怎么验证的」，只增不改
  - `scripts/snapshot.sh`：读 `version` 后把 skill 完整复制到快照目录，供日后 diff 与回滚；同日同版幂等。脚本与 `business-experience-report` 共用同一份实现（按自身位置推导 skill 目录，不写死技能名）
- `SKILL.md` 新增「维护与版本管理」一节：三步动作 + 三点约定 + 分发注意事项

### 动机

本 skill 由 `天工.skill` 的岗位型流水线（J1→J5）生成，此前**只有 `version` 字段、没有变更记录与快照**。后果是：想知道「某次评审标准的调整改了什么」只能回溯对话记录（间接证据）；改坏了没有退路。同时它与 `business-experience-report` 存在调用关系（后者第 8 步会调用本 skill），两侧版本漂移会造成「报告按新版规则、评审按旧版标准」的错配，因此版本可查是刚需。

### 验证

- 快照与 skill 目录逐文件 MD5 一致
- `tiangong-skill` 的 `verify-skill.py` 结构化校验仍 PASS（新增章节未破坏岗位型技能必需结构）
- 快照脚本负向测试沿用 `business-experience-report` 的结论：缺 `version` 给出可读报错并 `exit 1`；带引号的版本号能正确解析
